## Initiative A: Sherpa-CC Integration

**The big picture:** Close the loop so all Sherpa surfaces can start cycles, read agent memory, and push learnings back to CC — all over typed protocol contracts.

### What Already Exists

1. **CC already has a full cycle API** — 15+ REST endpoints (JWT + IAM), an MCP server with `start_cycle`/`list_cycles`/etc., and M2M Cognito credentials for programmatic access
2. **IDE already has a CC API client** (`SherpaClient`) with auth (SigV4 + Cognito) — currently used for chat/conversations, not cycles
3. **IDE already reads memory from S3** — `MEMORY.md`, daily notes, skills — via `promptLoader.ts`
4. **IDE already syncs context bidirectionally** — `ContextBroadcaster` pushes learned patterns to S3 and pulls from it
5. **Protocol has `CommandCenterProfile`** with `apiEndpoint`, `apiAuthMode`, `cognitoClientId` fields already defined (but unused in cycle flows)

### A1.8: @files Support (All Surfaces)

Explicit file-reference syntax in the chat input (`@filename`) to include file contents in the message context. Must work across IDE, TUI, and Web.

**Current state:**
- IDE auto-includes the active editor's first 200 lines and shows open files as badges — but has no `@`-mention syntax for explicitly referencing files by path
- TUI has no file-context injection at all
- Web has no file-context injection at all
- No surface has a `@file` autocomplete or file picker triggered from the prompt input

| # | Work Item | Where | Notes |
|---|-----------|-------|-------|
| A1.8a | Define `@file` resolution protocol: syntax, path resolution, content inclusion format | `sherpa-protocol` or `sherpa-core` | e.g., `@src/index.ts` resolves relative to workspace root, content injected as a user-message prefix or tool-like block |
| A1.8b | Path safety: restrict to workspace directory by default, require explicit permission to escape | `sherpa-core` (platform adapter level) | Workspace root boundary enforced. Escape could be a setting or per-request approval |
| A1.8c | Glob/directory support: `@src/components/` includes file listing, `@**/*.test.ts` includes multiple files | `sherpa-core` | With size limits (max chars, max files) |
| A1.8d | IDE implementation: autocomplete on `@`, file picker, resolve via VS Code workspace APIs | `nevado-sherpa-ide` | Can leverage existing `getOpenFilesInfo` pattern but extend to arbitrary paths |
| A1.8e | TUI implementation: autocomplete on `@` in Ink input, resolve via filesystem relative to cwd | `agent-workflow/apps/tui` | Tab-completion in terminal, respect workspace boundary |
| A1.8f | Web implementation: autocomplete dropdown, resolve via runtime API (new endpoint to list/read files within workspace) | `sherpa-web` + `agent-workflow/apps/runtime` | Web can't read files directly — needs runtime to serve file listing/content |
| A1.8g | Content truncation/summarization for large files | `sherpa-core` | Configurable max chars per file, total budget across all @-referenced files |

**Safety requirements:**
- Default: only resolve paths within the workspace directory (workspace root = boundary)
- Symlinks that escape workspace must be rejected or require approval
- Explicit permission model for escaping workspace (e.g., `@~/some-global-file` requires user confirmation)
- Path traversal (`../../../etc/passwd`) must be blocked at the resolution layer

**Design decisions needed:**
- **Where does resolution live?** If in `sherpa-core`, the platform adapter already has path-traversal prevention. Extend that.
- **How are contents injected?** Options: (a) prepended to user message as a fenced code block, (b) as a structured content block the engine understands, (c) as a synthetic tool result (like a pre-executed `readFile`)
- **Autocomplete data source for Web:** Runtime needs a file-listing endpoint scoped to the session's workspace. This partially exists (the `listFiles` tool) but isn't exposed as an API for the frontend.

### A3: Session Handoff (Cross-Surface Resume)

The desired outcome: sessions visible in CC and all surfaces, switchable so a session started in the IDE can be picked up in Web/TUI and vice versa.

**Current session persistence by surface:**

| Surface | Session Store | Persists? | Resumable? |
|---------|--------------|-----------|------------|
| **IDE** | SQLite (`.sherpa/sessions.db`) | Yes | Yes (local only) |
| **TUI (local mode)** | `FileSessionStore` (`~/.config/nevado/`) | Yes | Yes (local only) |
| **Runtime server** (TUI remote / Web) | `InMemorySessionStore` (oversight) | No | No — lost on restart |

The runtime using `InMemorySessionStore` is an oversight — `FileSessionStore` is available in `@nevadoai/sherpa-core` and the EC2 deployment has persistent disk. This is a one-line swap.

**What already works:**
- IDE broadcasts session *metadata* to S3 (`sessions/{app}/{id}.json`) — CC already renders these as read-only cards
- `AgentEngine.run()` handles resume natively (detects prior messages, fixes dangling tool uses)
- `FileSessionStore` in SDK persists everything needed (sessions.json + messages/{id}.json)
- Protocol types (`AgentSession`, `SessionMessage`) are shared across all packages
- TUI local mode already uses `FileSessionStore` — proves the pattern works

**Gaps:**
- Runtime oversight: swap `InMemorySessionStore` to `FileSessionStore` (trivial fix)
- Messages are not broadcast — S3 gets metadata only, full transcript stays local to each surface
- No shared session addressing or "adopt/import foreign session" flow
- Workspace state: resuming needs the same files, but no commit SHA or diff is recorded
- Session data definition: what fields are needed to support being picked up by another surface?

| # | Work Item | Where | Notes |
|---|-----------|-------|-------|
| A3.1 | Fix runtime to use `FileSessionStore` | `agent-workflow/apps/runtime` | One-line swap. Immediate fix for session loss on restart |
| A3.2 | Define session handoff data requirements in protocol | `sherpa-protocol` | What must a session record contain to be resumable from another surface? (`commitSha`, `hasTranscript`, `resumable` flag, workspace state) |
| A3.3 | Canonical message persistence format | `sherpa-protocol` | Formalize `EngineContentBlock[]` as the storage format all surfaces write/read |
| A3.4 | Broadcast messages to S3 (not just metadata) | IDE first, then SDK-shared | Extend `SessionBroadcaster` to upload transcript. IDE already sanitizes for SQLite (drops images, truncates tool results) — same logic |
| A3.5 | Shared session store implementation (S3-backed) | `sherpa-core` or new package | `FileSessionStore` pattern but backed by shared S3. Enables any surface to read any session |
| A3.6 | "Resume foreign session" flow on runtime | `agent-workflow/apps/runtime` | Fetch session + messages from shared store, clone repo at recorded branch, run engine with loaded context |
| A3.7 | CC UI: "Resume in Terminal" action on session cards | `command-center` frontend | Currently read-only. Add action that creates a runtime session pre-loaded with broadcast messages |
| A3.8 | IDE: resume a session from another surface | `nevado-sherpa-ide` | Pull session from shared store into local SQLite, continue |
| A3.9 | Workspace state handoff: commit SHA, branch, uncommitted changes strategy | Protocol + all surfaces | Resuming surface needs the same file state. Options: require committed state, or broadcast a stash |

**Key design decisions needed:**
- **Push vs pull for messages?** (a) Broadcast full transcript to S3 continuously, (b) shared store with on-demand query, (c) hybrid — metadata push, messages pull on resume
- **Workspace continuity:** Does resuming require a clean commit point? Or is branch + HEAD SHA enough (uncommitted changes lost)?
- **Conflict resolution:** What happens if two surfaces try to resume the same session simultaneously?

### Open Questions — Initiative A

1. **Where should the CC client live?** New `sherpa-cc` package keeps the dependency optional. Extending core makes it batteries-included. Tradeoffs around package size and optional dependencies need discussion.
2. **Is the existing cycle API sufficient for IDE use?** The MCP server already wraps it. The real work may be #A2.6 (IDE client), not new CC endpoints.
3. **S3 memory vs CC API memory?** The IDE already reads from S3. The CC `AgentMemory` class adds supervisor feedback and structured retrieval. Is the richer version needed, or is S3-direct fine for now?
4. **Does CC auto-ingest from S3?** If `ContextBroadcaster` pushes to `context/{app}/learned/` and CC's knowledge base reads from there, knowledge submission (#A2.3) may already work.
5. **Real-time progress:** CC polls today. Is that acceptable for IDE-triggered cycles, or does the IDE need push notifications (WebSocket/SSE)?
6. **Priority: SDK-first or CC-on-IDE-first?** SDK extraction (A1) is foundational but larger. A2 can land for IDE-only first and extract later.

## Initiative D: Embedded Agents / Revenue Wedge

### What Exists Today

**Architecture:** Single-tenant by design — isolation via separate EC2 per customer AWS account. Zero multi-tenant logic within the application.

| Dimension | Current State | Gap |
|-----------|--------------|-----|
| Auth | Hardcoded `dev-user`, TODO stub | Real identity + tenant association |
| Session isolation | Filesystem directory only | No process/container boundary |
| Settings | Global singleton per process | Per-deployment settings needed |
| Credentials (AWS) | Single IAM role for all sessions | Per-customer credential vending |
| Credentials (GitHub) | Single App installation, shared hosts.yml | Per-customer GitHub Apps |
| System prompt/persona | One S3 prefix for all | Per-tenant prompt loading |
| Data at rest | In-memory, shared Maps | Tenant-partitioned persistent store |
| Resource limits | Global `maxConcurrentSessions` | Per-tenant quotas |

**Key insight:** The "multi-tenant" item may be misframed. The architecture *is* isolated (one instance per customer). What's missing is per-deployment customization, deployment automation, and central management.

## Unresolved Questions (Decisions Needed Before Work Begins)

### 1. Auth / Identity Across Surfaces

Who is "Tyler" across IDE (AWS SSO), CC (Cognito), and runtime (hardcoded `dev-user`)? Today each surface has its own identity model with no mapping between them.

**Blocks:** A3 (session handoff — who can see/resume whose sessions?), D #16f (per-deployment auth), D #19 (Slack — who is the bot acting as?), metering (who gets billed?)

**Decision needed:** Is there a single identity provider, or a mapping layer? Does CC Cognito become the source of truth? Do IDE/TUI just need to prove they're the same AWS SSO principal?

---

### 2. MCP vs Typed SDK Client for CC Integration

The CC MCP server already exposes `start_cycle`, `list_cycles`, `get_cycle_status`, `approve_plan`, `iterate_cycle`, `cancel_cycle`, `create_pr`, `approve_pr`, `merge_pr`. The IDE already connects to MCP servers. The TUI has MCP tool specs in the engine.

**Blocks:** A2.4 (where does the CC client live?), A2.5-A2.8 (how each surface wires up)

**Decision needed:** Is A2.4 (new typed SDK CC client) duplicating what the MCP server already provides? Should the integration path be "connect to CC's MCP server" rather than "build a new HTTP client in the SDK"? Tradeoffs: MCP gives tool-calling semantics (good for agent-initiated), typed client gives programmatic access (good for UI-driven).

---

### 3. Notification / Async Completion

Cycles take minutes to hours. Session handoffs are async. If you trigger a cycle from the IDE and walk away, how do you know it's done? If someone picks up your session, how are you notified?

**Blocks:** A2.6 (IDE cycle triggering UX), A3.7 (CC resume action — what tells the original surface?), D #18 (claims agent reporting back to adjusters)

**Decision needed:** What's the notification channel? Options: (a) email via CC, (b) VS Code notification when IDE is open, (c) Slack (ties to #19), (d) push via WebSocket if surface is connected, (e) poll. Likely a combination — but which is the minimum viable path?

---

### 4. Metering / Usage Tracking for Customer Billing

Initiative D targets $5-15K/mo revenue. Token counts exist per-session (`TokenUsage` in protocol, tracked by engine) but there's no aggregation, no per-customer reporting, and no billing pipeline.

**Blocks:** D #17 (customer deployment — without metering, you can't invoice), D #18-19 (productized agents need usage visibility)

**Decision needed:** What's the billing model? Per-token? Per-session? Flat fee + overages? Where does metering data land — CC database? A dedicated pipeline? Does the customer see their own usage?
